# План уроков: multi-reestr (Jmix 3.0.3)

Каждый урок заканчивается коммитом и тегом `lesson-NN`; на теге проект собирается и проходит тесты, с любого тега можно продолжить курс.

Модель данных (сущности и перечисления) описана заранее в [model/OVERVIEW.md](model/OVERVIEW.md) и создаётся в начале курса в визарде Jmix Studio.

## Часть 1. Основа и чтение старой базы

1. **Каркас.** Проект Jmix 3.0.3 на Java 21, основная БД приложения, пользователь admin, структура модулей.
2. **Второй DataSource `legacy`.** Подключение к БД MultiReestr только на чтение, без Liquibase, через `NamedParameterJdbcTemplate`. Защита от записи на трёх уровнях: драйвер, Hikari, пользователь БД.
3. **Тестовый стенд.** Testcontainers `postgres:9.6`, схема из бэкапа, наборы данных по 10 эталонным извещениям; проверка `readOnlyMode=always`.
4. **Номер извещения.** Value object `NoticeNumber`: нормализация номера, юнит-тесты (пробелы, «№»).
5. **Поиск извещения.** `NoticeLookupService`: поиск записи и выбор оригинала среди дублей и копий; голден-тесты на 10 номерах.
6. **Полная карточка.** DTO-сущности `@JmixEntity`: лоты, спецификация и КТРУ, протоколы, контракт, исполнение, оплаты. Связи по тексту номера и полиморфный `reestrid`.

## Часть 2. Интерфейс

7. **Экран поиска** на Flow UI: по номеру, а без номера — по дате и названию.
8. **Карточка извещения.** Вкладки по блокам, переходы через `ViewNavigators`.
9. **Выгрузка в Excel.** Свой экспорт на Apache POI, два листа, как в `notices.xlsx`.
10. **Роли и доступ.** `@ResourceRole` для специалиста и администратора правил.

## Часть 3. Сроки

11. **Производственный календарь.** Собственный (без аддона Business Calendar — он требует Enterprise): `CalendarDay` хранит только исключения, интерфейс `WorkingCalendar` по образцу API аддона, импорт с xmlcalendar.ru, тесты на переносах.
12. **Движок сроков.** `DeadlineCalculator`: событие-якорь, смещение, календарные или рабочие дни, ст. 191 и 193 ГК РФ. Пример «пятница/суббота» — тест.
13. **Сроки на реальных замечаниях.** Замечания 1, 6 и 9 на настоящих датах.

## Часть 4. Бизнес-правила

14. **Модель правил.** Шаблон, правило, версия, даты действия, серьёзность, ссылка на норму.
15. **Первые шаблоны:** «ОКПД2 из перечня — нужен запрет» (ПП 1875), «характеристики только из КТРУ», «нет структурированного описания».
16. **Редактор правил в UI.** Пользователь создаёт правило из шаблона и заполняет списки, в том числе импортом из Excel.
17. **Прогон на истории.** Пробный запуск правила на старых данных и отчёт о находках.
18. **Проверка извещения по кнопке** — сценарий «создал извещение, система проверила».

## Часть 5. Контроль

19. **Реестр нарушений.** Статусы, отметка «принято к сведению», пояснения со ссылками на нормы.
20. **Проверка по расписанию** через Jmix Quartz, в первую очередь сроки поставки и приёмки.
21. **Оповещения в приложении.** Счётчик новых нарушений в меню. Почта (аддон Email Sending) не реализуется — только рассказываем.
22. **Финал.** Сквозной сценарий на эталонных данных, сборка и развёртывание на машине пользователя.

## Не используем

Платные/лишние аддоны: Business Calendar, Notifications (Enterprise), Audit (хватает трейтов ядра и `RuleVersion`), Email Sending (только обзор).
